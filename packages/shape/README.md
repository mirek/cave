# @cavelang/shape

Shape expectations and knowledge health (spec §20): schema as claims,
checked against the store's own `EXTENDS` taxonomy — plus the read that
looks at everything the append-only model keeps side by side, and alias
discovery (spec §27), which proposes what §13.6 should merge.

Expectations are ordinary in-band claims on the `EXPECTS` meta-verb
(standard prelude, §20.1):

```cave
service EXPECTS owner        ; instances carry HAS owner: …
service EXPECTS USES         ; instances appear as subject of a USES claim
team EXPECTS PART-OF         ; met by a stored `org CONTAINS team-x` (§5.5)
team EXPECTS PART-OF #cardinality:one ; exactly one current parent
service EXPECTS latency #unit:ms      ; current value must use ms
microservice EXTENDS service ; instances of microservice inherit the shape
api-gateway IS microservice
```

`#cardinality:one` changes the compatible one-or-more default into exactly
one current match. It is primarily useful for relations because an attribute
claim key already has one current value. `#unit:<unit>` applies to attributes
and requires exact normalized-unit equality; unitless values and implicit
conversions such as `s` to `ms` do not satisfy it. Violations carry the
observed count and distinct units, so CLI and JSON reports explain the mismatch.

Runtime checks and generated clients share constraint validation. `cardinality`
allows one `one` or `some` value; `unit` allows one non-empty text value on attributes
only. `expectations`, `evaluate`, and `check` throw `TypeError` for malformed
current declarations instead of weakening them. Client generation collects the
same problems in its result. Gates roll back newly introduced malformed
declarations. If a malformed declaration already exists, append its correction
or retraction without the gate before resuming checked writes. Unrelated tags
retain their classification meaning.
Stored binary unit tags are malformed, including empty blobs or bytes that
spell a valid unit. Runtime checks reject them and client generation reports
the same declaration problem instead of inventing unit mismatches. Reads and
rejected gated writes leave the store unchanged; repairing the tag to text
restores validation on the same open store.
`cave generate --out` reports these schema errors before publishing output, so
an existing generated client remains intact. After repairing the declaration,
retry generation to replace the file with a valid client.

Equivalent active declarations from several source contexts collapse to one
client field. Positive confidence differences and explicit default cardinality
(`some`) do not change the generated bytes or schema digest. Conflicting current
units or cardinalities fail generation; correcting the conflicting series or
retracting a redundant declaration restores the same client when the normalized
schema is unchanged.

An evaluation lazily captures one version-aware vocabulary registry inside its
read snapshot and shares it across fact selection, index construction and entity
checks. Attribute-only shapes do not access vocabulary. New peer declarations
refresh the next evaluation that needs relations; relation checks do not issue
one SQLite cache check per instance. `scripts/shape-registry-bench.mjs` measures
100, 1,000 and 5,000 inverse-relation instances with five timed evaluations and
setup/result/history assertions outside timing. At 5,000 instances, local medians
fell from 19.73 to 18.53 ms on Node 24 and 20.41 to 18.37 ms on Node 26. This is
one relation-shape workload, not a general health-report performance guarantee.

`scripts/shape-attribute-registry-bench.mjs` checks the complementary case: one
attribute expectation after each peer commit with unrelated verb declarations.
Making the shared registry lazy avoids replaying those declarations for attribute
checks. At 3,000 declarations, five-sample medians fell from 34.86 to 4.94 ms on
Node 24 and 28.47 to 4.77 ms on Node 26. Setup, peer writes and result/history
assertions are outside timing. Remaining declaration/typing reads still scale
with relevant store indexes; this change does not make all evaluations constant-time.

Shape evaluation first probes for any `EXPECTS` row. If none exists, it returns
an empty evaluation without materializing the store. The probe runs on every
evaluation, including both sides of a gated write, so newly introduced shapes
still receive validation and can roll the write back. Historical, retracted,
or qualified declarations first read current declaration metadata. If no active
expectations survive those checks, evaluation returns without a fact snapshot.
Reactivation is observed on the next evaluation; no result is cached. With
gated writes, reactivating a historical expectation is checked against the
batch's resulting facts. A newly introduced violation rolls back the whole
batch, including its expectation and vocabulary changes; providing the missing
value in the same batch can satisfy the gate. With
active expectations, the probe plus four snapshot reads keep query count
constant regardless of the number of instance/expectation pairs. Ordinary
facts materialize only fields needed for target and value indexes. Snapshot
SQL filters confidence and negation before projection; those columns are not
copied into JavaScript or checked again while building indexes. Snapshot
selection retains `IS`/`EXTENDS` facts and the attribute or canonical relation
slots named by active expectations, including the primary side of inverse
relations. Every candidate is checked against its complete claim-key history
before accepting its current positive version, so a retraction never revives
an older value. A separate
declaration read retains complete rows for report provenance. Filtering
`EXPECTS` before current-series grouping is safe because the verb is part of
claim identity. Snapshot results are freshly read for each evaluation. General current-row reads use the store package’s shared
`QuerySql.current()` fragment, keeping latest-claim selection consistent with
other consumers.
Observed-value indexes include only attributes and relation directions requested
by active expectations. Taxonomy facts still build the target graph; `IS` and
`EXTENDS` also enter observed indexes when explicitly required as relations.
Forward and inverse expectations can share a primary verb without losing either
direction, and each evaluation derives its required indexes afresh.
Standalone `evaluate` keeps its declaration, qualifier, and fact reads in one
read savepoint, including on read-only stores. Peer commits cannot mix older
expectations with newer facts in the same result; the next call observes the
new state. The savepoint nests inside health reports and gated writes without
committing their outer transactions.
Constraint-tag and qualifier-edge reads are restricted to those declaration
IDs, using one bound JSON array rather than one SQL parameter per declaration.
This preserves tag order and qualifier exclusions without materializing
unrelated action lineage or fact tags on every gated write.
Taxonomy-child and per-type expectation groups append to evaluation-local
arrays, preserving declaration order without repeatedly copying each growing
group. This keeps group construction linear for wide taxonomies and types
with many expectations; it does not cache state between evaluations.

An incremental gate would need to track more than the subjects of effect rows.
An attribute change affects that subject's expected slot; a relation change can
affect both its subject's forward slot and its object's inverse slot. Changes to
`IS` or `EXTENDS` can change which inherited expectations target an entity,
while expectation declarations, their constraint tags and qualifier edges, and
vocabulary mappings can change the checks themselves. Retractions and
reactivations must use the resulting current claim versions. For executions with changed effects, the action gate
therefore still compares complete before/after violation sets. Entirely
unchanged actions skip both snapshots; the baseline is deferred until the
first effect that will write. A future narrowed
implementation needs equivalent dependency tracking, with full evaluation when
those dependencies cannot be established; no incremental result cache is
implemented here.

A local CPU profile of `scripts/automation-bench.mjs --shapes` on Node 26.5.0 /
SQLite 3.53.3, macOS arm64, sampled about 20.2 seconds across its 100, 500, and
1,000-event fixtures. Aggregated self samples placed about 52% in `shapeState`,
10% in `observedIndexes`, and 9% in `targetIndexes`. Native synchronous database
work is attributed to its JavaScript caller, so the snapshot share includes
that work; these percentages are diagnostic observations, not guarantees.
All benchmark correctness and quiet-cycle assertions passed under profiling.
This motivated narrowing snapshot selection while preserving current-version
selection, inverse relation slots, taxonomy inheritance, and qualified
declarations. A subsequent 1,000-event shaped benchmark completed in 14.28 s
with all checks satisfied and zero quiet-cycle writes; timings remain local
observations. A cache across evaluations
would additionally need correct invalidation on writes and rollback; the
current implementation retains fresh reads.

```ts
import { check, gatedIngest } from '@cavelang/cli/shape'

check(store)
// → { violations: [{ entity: 'api-gateway', via: 'microservice',
//      expectation: { type: 'service', kind: 'attribute', name: 'owner', … } }],
//     stale, review, disagreements, coverage }

gatedIngest(store, 'cache IS service', { source: 'cli' })
// → { ok: false, violations: […] } — rolled back atomically (§20.3)
```

## The report (§20.2)

`check(store, { staleDays?, now? })` reads, never writes. `staleDays` must be
finite and non-negative (fractional days are allowed); `now` must return a
finite millisecond timestamp. Invalid options throw `TypeError` before database
reads. All report sections share one read snapshot, including on read-only
connections. The read savepoint nests within a caller transaction without
committing its writes and attempts release on both success and error. WAL allows a
peer writer to commit while a report reads its earlier snapshot; rollback-journal
mode can delay writer commits until that read finishes. The next report sees
new commits.
Read snapshots used by expectation listing, evaluation, health reports, client
generation, alias discovery, and judge prompts attempt release once. If a read
and release both fail, an `AggregateError` retains the read error as its cause
and first entry and the release error second. A release-only error propagates
directly; it does not produce a successful report. The report contains:

- **violations** — (instance, expectation) pairs currently unsatisfied;
  the failing section (`cave check` exits 1 on any).
- **stale** — current beliefs whose tx timestamp (UUIDv7 encodes
  wall-clock ms) is older than the horizon (default 90 days). Appending a
  fresh belief to the series resets the clock.
- **review** — current beliefs at `conf 0.3–0.7` (§13.5).
- **disagreements** — cross-series conflicts inside alias closure groups
  (§13.6 keeps aliased series separate; this is what looks at them). Alias
  closure uses iterative path compression, so long chains do not consume
  the JavaScript call stack. One ordered read groups current non-alias rows
  in memory, avoiding a SQL parameter per group member. The report compares
  same verb+attribute with different values, or same verb+object asserted
  by one name and negated by another. A report requires a conflicting pair
  whose originating alias names differ; actor forks within one name remain
  visible as belief series but are not mislabeled as alias disagreements.
  Bucket construction and conflict comparisons take linear time in their
  row counts, including large groups that agree. Reports retain every
  participating row, including independently attributed copies.
  Series scoped to different
  non-`src:` contexts describe different facts and never disagree; actor
  provenance stamps (§9.5) are provenance, not scope. Grouping preserves
  context boundaries with a JSON tuple, including separator characters
  supplied through the structured API.
  Scope contexts for participating rows are fetched in one batch using a JSON
  list of claim IDs, so SQL read count does not grow with the number of conflict
  slots and does not consume one bind parameter per claim. The regression with
  1 and 100 scoped conflict slots uses nine reads for either health report;
  row processing and returned evidence still grow with the data.
  A separate 33,002-evidence-row regression exercises the context batch beyond
  32,766 claim IDs, retaining a conflict at the end of the batch while excluding
  its unrelated staging series.
- **coverage** — the §17.6 precursor: row/fact/belief-state counts,
  confidence distribution, typed-entity fraction, expectation
  satisfaction.

Coverage computes fact counts, belief-state counts, low-confidence counts, and
mean confidence in one aggregate over current versions. The mean and
low-confidence counts include current negative beliefs, while retracted rows
are excluded from both; an empty store retains zero counts and a null mean.
Entity and typed-entity coverage share one narrow read of current believed
subjects, objects, verbs, and polarity. Names are deduplicated across actor
series; quoted literals and verb tokens are excluded. Negative beliefs can
mention entities, but only positive `IS` relations count as typings.

## Write gating (§20.3)

`gatedIngest(store, text, { strict?, source? })` reserves the write transaction
before reading baseline violations, then appends, re-evaluates,
and rolls back (savepoint transaction, in-memory registry included) when
the append *introduces* violations that were not present before —
including against expectations the text itself declares. Pre-existing
violations never block: the gate compares, it does not demand a clean
store. `cave add --check` is the first enforcement point; action
preconditions reuse the same mechanism.
The shared evaluation registry stays local to that evaluation. If a batch adds
an inverse declaration that repairs one violation but introduces another, rejection
also discards that inverse: the next evaluation sees the original vocabulary and
violations. A corrected retry can add the declaration and required data together.
An ordinary `{ ok: false }` result means the rejected append was rolled back.
If rollback itself fails, the gate throws an `AggregateError` retaining the shape
rejection as its cause and the rollback failure as the second error. It does not
report a completed rollback. The transaction owner must finish cleanup, for
example by rolling back its enclosing transaction or closing the store before
reopening it. Recovery tests exercise both paths and verify unchanged persisted
history and vocabulary before a corrected write succeeds.

`violationKey` compares the entity, expectation type, kind and name as a JSON
tuple. Component boundaries remain distinct even when names contain separator
characters, so an existing violation cannot mask a new one in either gate.

## Typed client generation (§20.4)

`generateClient(store)` deterministically turns current expectations into a
versioned TypeScript module; `cave generate --db k.db --out cave-client.ts`
writes the same bytes. Generated interfaces preserve exact field names,
and readers emit own data properties even for names such as `__proto__`,
without changing the result object's prototype. They preserve
attribute text/number/unit values, inverse-aware relations, arrays for the
compatible `some` cardinality, and runtime-checked scalars for
`#cardinality:one`.
Compiler checks cover both the generated module and a consuming TypeScript
program: scalar/array cardinality, literal unit types, read-only properties and
collections, and rejection of undeclared fields. These static checks complement
the generated readers' runtime unit and cardinality checks.
Each generated reader holds one deferred read snapshot across all its fields,
including relation reads, so a concurrent commit cannot mix database states in
one returned object. The snapshot releases on success or validation failure,
works on read-only connections, and nests inside a caller's transaction without
committing it. Generated readers also preserve simultaneous query/validation and
release failures in `AggregateError`, with the read error first and as cause.
Regenerate previously emitted client files to receive this
behavior; the embedded digest identifies the schema, not the generator's code.

```ts
const generated = generateClient(store)
if (!generated.ok) throw new Error(generated.problems.join('\n'))
// generated.version === 1
// generated.digest === SHA-256 of the normalized versioned schema
// generated.code is the complete TypeScript module
```

The file embeds its normalized schema, format version and digest. Sorting uses
code-point order, so append order and locale do not alter output. Conflicting
declarations, invalid/repeated cardinality or unit tags, relation units,
unsupported versions, and type-name collisions are reported together before
any CLI output file is written. Text and CAVE-Q stay primary; this module is a
reviewable derived artifact, regenerated when `EXPECTS` claims evolve.
Generated interface names also cannot be `Store` or `CaveValue`: those type
names belong to the emitted client infrastructure. Rename the CAVE type when
generation reports this conflict. Value-only helper names do not reserve
TypeScript interface names.

Field identity uses the complete type, kind and property-name tuple. Embedded
NUL characters in accepted names cannot make distinct fields collide; generated
property names retain their JSON escapes.

The package tests compile a generated module with the workspace TypeScript
compiler in strict NodeNext mode, alongside executing generated readers against
real stores. This checks generated type bindings as well as runtime behavior.
Client generation and expectation listing use a declaration-only snapshot:
three SQL reads load current declarations, constraint tags and qualifier edges
within one read savepoint, without materializing ordinary facts. A peer's new
declaration version and qualifier edges cannot be mixed with older declaration
rows; the next snapshot observes the new state. Generation keeps this snapshot
open while resolving relation mappings from the verb registry, so a concurrent
inverse declaration cannot be paired with an older cardinality. Read errors
release the snapshot, and generation inside a caller transaction preserves its
rollback boundary. Generation reuses the loaded tags. Grouped fields append in place,
preserving sorted output without repeatedly copying growing arrays.

## Alias discovery (§27)

`suggestAliases(store, { minScore?, limit? })` requires a finite score in
0..1 (default 0.6) and, when supplied, a positive safe-integer limit. Invalid
options throw `TypeError` before reading the store, including empty stores.

Under LLM extraction the same entity drifts across names; discovery
finds the pairs, review decides them:

```ts
import { suggestAliases, writeSuggestions } from '@cavelang/cli/shape'

suggestAliases(store)
// → [{ entity: 'grandma-maria', canonical: 'maria', score: 0.7,
//      confidence: 0.35, signals: [{ kind: 'tokens', … }],
//      line: 'grandma-maria ALIAS maria #suggested @ 35% ; segments of maria within grandma-maria' }]

writeSuggestions(store, suggestAliases(store))  // append, stamped @src:suggest/alias
```

Suggested lines use the canonical emitter to preserve entity payloads. ALIAS
is undirected: if the preferred target looks like a numeric/date value, the
line reverses its endpoints, for example `42 ALIAS 4-2`. The suggestion's
`entity` and `canonical` fields still report the less- and more-established
names. Scores, confidence and evidence are unchanged. If neither endpoint can
be represented as an entity object (for example `42` and `43`), discovery
throws an explicit representation error without writing. Lines are rendered
only after ranking and applying the requested limit: an unsupported pair outside
the selected results does not block a valid higher-ranked result. Selected
unsupported pairs still report the error. It does not return
a value claim or convert either name to a text literal. This is a boundary of
the current entity-object syntax, not an automatic renaming policy.
`node scripts/alias-suggestion-emission-audit.mjs` checks six discovered pairs
and one unsupported-pair error in isolated stores, including relation endpoints
and repeat-discovery suppression.

To retract a written suggestion, preserve the actual emitted subject/object
order and its contexts, including `@src:suggest/alias`, while setting confidence
to zero. For example, retract a reversed numeric-name suggestion with
`42 ALIAS 4-2 @src:suggest/alias @ 0%`. Do not reconstruct its direction from
the preferred-name metadata: alias traversal is undirected, but stored claim
series retain direction and contexts. An independent confirmation in another
series remains linked when the suggestion's series is retracted.

`writeSuggestions` reserves one transaction and rechecks alias history in both
directions before appending. It skips reviewed pairs and duplicate input pairs,
returning the actual appended count. Before writing, every fresh line must parse
as exactly one positive ALIAS relation between its proposed entity names, in
either direction. Value payloads, different endpoints, extra claims, negation,
zero confidence and diagnostics reject the whole fresh batch without appending.
The check captures the submitted names and text once. Validated claims are
canonically emitted before joining the batch, preserving metadata and comments
while preventing supplied indentation from creating grouping edges between
suggestions. Reviewed and duplicate pairs retain their existing skip behavior. Retained suggestions cannot revive a link
rejected while an external judge was running. This recheck protects recorded
pair decisions; it does not rerun scoring or the judge against changed evidence.

- **Signals are deterministic and explainable** — normalized-name
  equality, segment reorder/containment, prefixes, edit similarity
  (with a differing-segments guard: `grandma-mria` drifts,
  `north-tower`/`south-tower` doesn't), shared *rare* textual attribute
  values; shared relation neighbors boost a candidate, never create one.
  Numeric scalars and trajectories such as `10 -> 20 ms` do not provide
  rare-text identity evidence. Explicitly quoted text remains eligible even
  when its contents resemble a measurement.
  Neighbor evidence preserves complete text and code literals, including
  spaces, in both signal details and the suggested claim's comment.
  Each discovery call indexes rare-value evidence by entity pair once, retaining
  at most two signals per pair. Candidate scoring does not rescan every stored
  attribute value; a later call rebuilds the index from current beliefs.
- **Suggestions are questions**: confidence is `score/2` clamped to
  0.3–0.5 — the §20.2 review band — and the evidence rides in the
  line's comment.
- **Decisions stick**: any recorded `ALIAS` history between two names
  (merged, rejected `ALIAS NOT`, or unmerged `@ 0%`) excludes the pair,
  as do closure-group membership, a direct relating claim, and
  scope-parent names.
- **The judge stays out-of-band** (§19.5): `judgePrompt(store,
  suggestions)` / `parseJudgeReply(reply, count)` define the contract;
  the CLI wires any shell agent to it (`cave suggest-alias --agent`).
  Prompt assembly captures candidate order, text and both names before opening
  its read snapshot, so caller mutations during evidence reads cannot mix a
  candidate description with another pair's evidence.
  All current-claim evidence in one prompt shares a read snapshot, including
  both sides of every suggestion. A concurrent update cannot manufacture a
  contradiction between older and newer evidence. The snapshot closes before
  the external judge runs; retained suggestion scores and comments still
  describe the earlier discovery, and writing rechecks pair history as above.
  Shared agent-layer reply extraction consumes complete JSON arrays, objects and strings before
  selecting array answers. Arrays embedded in objects such as `{"rejected":[1]}`
  or quoted strings such as `"[1]"` never become confirmations. Within an answer
  array, quoted and nested entries are discarded. The last eligible well-formed
  array still wins, with recovery after unfinished prose brackets or quotes.

Alias reply parsing uses the agent layer's shared JSON syntax index before
native decoding. This avoids repeatedly decoding overlapping malformed spans
without truncating replies or limiting recovery attempts. The index takes linear
work and memory; answer selection and JSON-container exclusions are unchanged.
`node scripts/alias-judge-parse-bench.mjs` runs three isolated samples per depth
and checks the recovered answer. Measured medians on macOS arm64:

| Malformed nesting | Node 24 before / indexed | Node 26 before / indexed |
|---|---:|---:|
| 1,000 | 10.88 / 0.95 ms | 13.37 / 1.06 ms |
| 2,000 | 33.61 / 1.13 ms | 41.40 / 0.76 ms |
| 4,000 | 120.54 / 0.72 ms | 147.68 / 0.82 ms |
| 8,000 | 439.31 / 1.52 ms | 546.23 / 1.55 ms |

These short samples include warm-up variation and measure parsing alone, not
agent latency. Regressions count decoded input bytes as well as checking answers;
a 20,000-level malformed prefix decodes only its valid final answer.

Discovery reads current evidence and all recorded alias decisions in one
deferred snapshot, including on read-only connections. It releases that snapshot
before pair scoring and on read failure; nested discovery preserves a caller's
transaction. Later calls observe committed changes, and writing suggestions
still rechecks decision history under its own write reservation.

Discovery computes each candidate name's normalized spelling, digitless form
and token set once per call, then shares them between candidate grouping and
pair scoring. Nothing is cached across calls or store changes. This reduces
repeated string processing while preserving the candidate pairs, thresholds,
signals and ranking. Large groups can still require quadratic pair comparisons.

Edit-distance scoring stops once a pair cannot meet the existing 0.75
similarity threshold. Length differences and a bounded diagonal search reject
non-matches early; qualifying pairs retain their exact UTF-16 distance and
score. Exhaustive short-string comparisons against a full matrix cover every
distance limit, with Unicode examples as well.

Rare-value evidence groups attribute name, stored value text and unit as a JSON
tuple. Structured attribute names containing newlines retain their boundaries
and complete names in evidence details instead of being split into value or
unit fields.

Pairs shared by several candidate groups are scored in their first shared
group. Duplicate-suppression storage grows with name/group memberships instead
of retaining a key for every compared pair. When `limit` is supplied, a heap
retains only that many best suggestions while scoring. Final sorting preserves
the exact score, name and stable tie order of an unlimited run followed by
slicing. Unlimited calls retain their ordinary result array and stable sort.
Discovery captures `minScore` and `limit` once before graph reads, so validation
and collection use the same values even when options have getters.
Pair-comparison time and unlimited result size can still grow quadratically.

## Design notes

- **Checking is a read; enforcement is opt-in.** §9.4 write-time
  tolerance is load-bearing — a store must accept claims about entities
  it has no shape for. Nothing here changes what `store.ingest` accepts.
- **Binding through the taxonomy only.** Targets are entities with a
  current positive `IS` claim into the type or its `EXTENDS+`
  descendants — no name globs, which would institute a shadow type
  system. Traversal visits every reachable type once, with no depth cutoff;
  cycles terminate and multiple paths do not duplicate instance checks.
  Subclass entities themselves are not instances.
- **Each expectation is its own claim key**, so shapes evolve append-only
  like everything else: retract with `service EXPECTS owner @ 0%`;
  history survives.
- **Constraints are tags, not a type system.** Only `#cardinality:one` and
  attribute `#unit:<unit>` have shape semantics. Omitting them preserves the
  original presence check, and unit conversion remains explicit elsewhere.
- **Evaluation materializes current belief once.** After the declaration
  presence probe, four SQL reads load narrow current facts, full current
  declarations, relevant tags, and declaration-excluding edges; taxonomy,
  inverse-relation, attribute, cardinality, and unit indexes are then built in
  memory. SQL statement count is therefore independent of
  instances × expectations. Gated ingestion performs one evaluation before
  its append and one after it, because pre-existing violations must remain
  distinguishable from newly introduced ones. Actions use the same complete
  comparison when an effect changes, taking the baseline immediately before
  the first write; unchanged actions take neither snapshot.

Run the deterministic large-shape benchmark with:

```sh
pnpm --filter @cavelang/shape bench:shape
```


For a read-only comparison of shape-fact SQL strategies, run
`pnpm bench:shape-query` from the repository root. It compares the current
correlated latest-row lookup with grouped selection over the relevant verbs
and attributes. Each fixture includes unrelated rows and final retractions;
the tool asserts identical ordered fact projections before timing 20 reads
per sample and emits three samples, their median, and query plans. Setup and
correctness assertions are outside the timed interval. Run it without concurrent
builds or tests.

| 1,000 | 1 | 37.3 ms | 49.4 ms |
| 1,000 | 10 | 129.7 ms | 113.0 ms |

The grouped alternative helps these deeper-history fixtures but loses on the
shallow-history fixture closest to the automation throughput workload. It was
therefore not substituted into evaluation. These timings measure only fact

threshold. Reducing repeated gates requires separate dependency and rollback
proofs; changing this SQL alone would still evaluate all affected snapshots.
